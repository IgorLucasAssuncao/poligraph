1. O servidor

VPS KVM 2 da Hostinger (2 vCPU, 8 GB, São Paulo), Ubuntu 24.04. Do sistema recém-instalado ao Coolify de pé, os passos 3 a 7 estão em infra/vps/configurar-vps.sh, que pode rodar de novo sem estragar nada:

bash configurar-vps.sh igor "ssh-ed25519 AAAA… igor-notebook-hostinger"
CLOUDFLARE_TUNNEL_TOKEN='…' bash configurar-vps.sh igor     # inclui o túnel (etapa 5)

Reinstalar o sistema do VPS apaga tudo: usuário, chaves cadastradas, configuração do SSH, fail2ban, o Coolify e o túnel. E troca a impressão digital do servidor: o SSH do computador passa a recusar a conexão com o aviso REMOTE HOST IDENTIFICATION HAS CHANGED. Depois de reinstalar, recomeçar do passo 2.

1. Chave SSH, no computador do autor

PS> ssh-keygen -t ed25519 -C "igor-notebook-hostinger"

Saem dois arquivos em C:\Users\igorl\.ssh\. O .pub é a chave pública: uma linha que começa com ssh-ed25519 e pode ser mostrada a qualquer um. O sem extensão é a privada e nunca sai do computador. Na conexão, o servidor manda um desafio, o computador o assina com a privada, e o servidor confere com a pública: a privada não trafega. Uma chave por computador: se um notebook se perder, apaga-se só a linha dele no servidor.

2. Criar ou reinstalar o VPS

No hPanel, escolher o sistema e colar a linha inteira do .pub no campo de chave SSH. A Hostinger oferece modelos com o Coolify já instalado; um modelo com outro aplicativo atrapalha (um Traefik avulso disputa as portas com o do Coolify). Se o servidor já existia, apagar a impressão digital antiga e conferir a nova pelo terminal do navegador do hPanel, que não depende do SSH:

PS> ssh-keygen -R IP-do-VPS
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

3. Primeira entrada, como root

PS> ssh root@IP-do-VPS
apt update && apt upgrade -y

Se pedir senha, a chave não foi aceita. Não insistir: entrar pelo terminal do navegador e colar a linha do .pub em /root/.ssh/authorized_keys.

4. Usuário próprio com a mesma chave

adduser igor
usermod -aG sudo igor
mkdir -p /home/igor/.ssh
cp /root/.ssh/authorized_keys /home/igor/.ssh/
chown -R igor:igor /home/igor/.ssh
chmod 700 /home/igor/.ssh && chmod 600 /home/igor/.ssh/authorized_keys

A senha do adduser é inventada na hora e serve só ao sudo, não ao SSH. Conferir numa segunda janela, sem fechar a primeira: ssh igor@IP-do-VPS entra sem pedir senha, e sudo whoami responde root.

5. SSH sem senha

sudo nano /etc/ssh/sshd_config.d/99-endurecer.conf
PermitRootLogin prohibit-password
PasswordAuthentication no
KbdInteractiveAuthentication no
sudo sshd -t && sudo systemctl restart ssh

O sshd -t recusa arquivo com erro antes de reiniciar. Root só por chave, e não PermitRootLogin no: o Coolify comanda o próprio servidor por SSH como root, com uma chave que ele mesmo põe em /root/.ssh/authorized_keys. Com no, ele perde o acesso e marca o servidor como inalcançável (Coolify, Servers, localhost, Validate).

6. fail2ban

sudo apt install -y fail2ban
sudo systemctl enable --now fail2ban

Bloqueia por 10 minutos o endereço que erra o login várias vezes. A configuração padrão do Ubuntu já cobre o SSH. As redes internas do Docker ficam de fora: o Coolify entra no próprio servidor por SSH a partir de um container, e um bloqueio dele derruba os deploys e as tarefas.

printf '[DEFAULT]
ignoreip = 127.0.0.1/8 ::1 172.16.0.0/12 10.0.0.0/8
' | sudo tee /etc/fail2ban/jail.d/redes-internas.local
sudo systemctl restart fail2ban

7. Firewall no painel da Hostinger

Em Segurança, Firewall: só a porta 22 (TCP), desde que o túnel da etapa 5 está de pé. Antes dele, eram 22, 80 e 443. Usa-se o firewall do painel, e não o ufw do sistema: o Docker cria regras próprias e passa por cima do ufw; o do painel fica fora da máquina. Conferir de fora:

PS> Test-NetConnection IP-do-VPS -Port 22      # True
PS> Test-NetConnection IP-do-VPS -Port 443     # False
PS> Test-NetConnection IP-do-VPS -Port 8000    # False

2. O Coolify

O painel que sobe e derruba os containers: liga o repositório, cria o banco e a aplicação, guarda as variáveis e publica cada versão. Ele controla o Docker, e só: usuários, SSH, firewall, túnel e atualizações do sistema continuam com o autor. Comanda o próprio servidor por SSH como root, com uma chave dele.

1. Instalar

Se o modelo do VPS já o trouxe, conferir; se não, o instalador oficial (instala o Docker se faltar):

sudo docker ps
curl -fsSL https://cdn.coollabs.io/coolify/install.sh | sudo bash

O docker ps lista coolify, coolify-proxy (o Traefik), coolify-db, coolify-redis e coolify-realtime. Um Traefik que não seja o coolify-proxy sai antes: docker compose down na pasta dele, ou docker rm -f.

O Traefik, que vem com o Coolify

É o container coolify-proxy. Não tem arquivo com as rotas do site: ele observa o Docker, e cada container leva nos rótulos (labels) a regra dele, escrita pelo Coolify a partir do campo de domínio. O painel é a exceção: a regra dele fica num arquivo em /data/coolify/proxy/dynamic/.

PeçaNo nosso caso
Entrypoint, a porta em que escutaA 80 da máquina, por onde chega o túnel. A 443 continua configurada, mas não recebe nada: está fechada no firewall
Router, a regra de endereçoHost(`registroaberto.org`) || Host(`www.registroaberto.org`) no site; painel.registroaberto.org no painel. A API e a migration não têm domínio, então não têm regra
Service, o destinoO container do site, porta 8080: é a "porta interna" do campo de domínio, a de dentro do container

Nada disso se edita à mão: o Coolify reescreve no próximo deploy. Para ver as regras de verdade:

docker inspect $(docker ps -q --filter "name=web-") --format '{{range $k,$v := .Config.Labels}}{{println $k "=" $v}}{{end}}' | grep traefik

2. Copiar o banco local (P87)

Antes do primeiro deploy, com o banco de produção vazio: se a migration rodar antes, as tabelas já existem e o restore entra em conflito. No computador do autor, com o Aspire parado, um Postgres 18 temporário abre o volume do Aspire e gera o dump. A senha vem dos user-secrets do AppHost (Parameters:postgres-password), sem aparecer na tela:

PS> podman run -d --name pg-dump-tmp -v <volume do Aspire>:/var/lib/postgresql postgres:18.3
PS> podman exec -e PGPASSWORD=… pg-dump-tmp pg_dump -U postgres -d poligraph -Fc --no-owner --no-acl -f /tmp/poligraph.dump
PS> podman cp pg-dump-tmp:/tmp/poligraph.dump C:\Users\igorl\poligraph.dump
PS> podman rm -f pg-dump-tmp
PS> scp C:\Users\igorl\poligraph.dump igor@IP-do-VPS:/tmp/

No VPS, infra/vps/restaurar-banco.sh confere o sha256, acha o container, o usuário e o banco, recusa banco que não esteja vazio, restaura, mostra as contagens e apaga o dump. Em 2026-10-15: 3,6 GB no local, dump de 193 MB, 8.319 parlamentares e 2.179.300 votos dos dois lados.

O dump foi do banco inteiro, e a P87 previa só as tabelas das fontes. Vieram também usuarios, segue, consentimentos, avaliacoes e tokens_email do ambiente local. Conferir e apagar em produção (apagar usuarios leva junto as que dependem dela):

docker exec -it NOME psql -U poligraph -d poligraph -tAc "select 'usuarios', count(*) from usuarios union all select 'avaliacoes', count(*) from avaliacoes"
docker exec -it NOME psql -U poligraph -d poligraph -c "delete from avaliacoes; delete from usuarios;"

Da próxima vez: pg_dump com --exclude-table-data para essas tabelas.

A POLIGRAPH_CHAVE_CPF da ETL em produção tem de ser a mesma do local: os cpf_hash copiados foram calculados com ela.

3. O compose

O docker-compose.prod.yaml monta três serviços a partir dos Dockerfiles de docker/:

  1. migrations aplica as migrations e as perguntas da curadoria e termina. Roda a cada deploy; sem migration nova, só confere. Termina com Banco: 8319 parlamentares, … perguntas ativas.
  2. api e api2, duas cópias iguais da API (decisão do autor, 2026-10-15), sobem só depois de a migration terminar bem, com o mesmo volume chaves-da-sessao: as duas abrem o mesmo cookie de sessão.
  3. web é o site, o único com domínio. O nginx dele divide o /api/ entre as duas cópias e, se uma não responde em 2 segundos, manda para a outra.
  4. etl é a carga de dados, parada (sleep) à espera das tarefas agendadas, com o cache no volume etl-cache.
  5. observabilidade é o Grafana tudo em um (Grafana, Loki, Tempo, Prometheus e o coletor OpenTelemetry), com os logs, rastros e métricas da API e os logs da ETL. Teto de 2 GB de memória; logs e métricas guardados por 30 dias. Passo a passo em infra/vps/grafana.md.

O primeiro deploy leva vários minutos, porque o VPS monta o .NET, o site e a migration. Cada deploy processa os três serviços, com alguns segundos sem API: é a escolha para subir rápido (decisão do autor, 2026-10-15). Quando o CI publicar as imagens (P23), cada peça vira aplicação própria, sem queda.

4. A carga agendada

A rotina já existe na ETL (rotina.py, Pendência 64): o Coolify só a dispara, dentro do serviço etl. Explicação em infra/vps/coolify-tarefas.md; valores prontos para colar em infra/vps/coolify-tarefas-colar.md. Na aplicação, Scheduled Tasks:

NameCommandFrequencyServiço
rotina-semanalpython -m poligraph_etl rotina --frequencia semanal0 3 * * 1, segunda às 3hetl
rotina-mensalpython -m poligraph_etl rotina --frequencia mensal0 3 2 * *, dia 2 às 3hetl
  • A semanal traz as votações do ano, as simbólicas e as palavras-chave novas. A mensal acrescenta o dinheiro, a população e o grafo; em janeiro, abril, julho e outubro, o cadastro da Receita; depois de eleição geral, o TSE.
  • Toda rotina termina com conferir, que falha se um total não fechar com a fonte, e com limpar-cache: downloads com mais de 35 dias e cópias de procedência com mais de 180 saem do volume, e do cadastro da Receita fica só o mês mais recente.
  • Uma trava do Postgres impede duas rotinas ao mesmo tempo: quando a semanal e a mensal caem juntas, a segunda espera.
  • Precisa de POLIGRAPH_CHAVE_CPF, a mesma do local. Em Notifications, ligar o aviso de falha de tarefa agendada.
  • A primeira mensal, com o cache vazio e o cadastro da Receita, roda à mão, num horário de pouco acesso.

Como serviço do sistema, sempre: o service install registra o conector no systemd, e ele continua rodando com o SSH fechado e sobe sozinho quando o VPS liga. Rodar cloudflared tunnel run no terminal prende o túnel à sessão: fechado o SSH, o site cai com o erro 1033. Para o sistema reiniciá-lo a cada queda:

sudo mkdir -p /etc/systemd/system/cloudflared.service.d
printf '[Service]
Restart=always
RestartSec=5
' | sudo tee /etc/systemd/system/cloudflared.service.d/sempre.conf
sudo systemctl daemon-reload && sudo systemctl enable cloudflared && sudo systemctl restart cloudflared
systemctl is-enabled cloudflared; systemctl is-active cloudflared    # enabled, active

O túnel fica Healthy no painel. O configurar-vps.sh faz tudo isso com CLOUDFLARE_TUNNEL_TOKEN.

9. Rede e portas

Como os containers se encontram dentro do VPS, por que duas cópias da API usam a mesma porta sem conflito, e o que decide se um container ocupa uma porta da máquina. Os IPs abaixo são exemplos: o Docker sorteia os de verdade a cada deploy, e no fim da página estão os comandos para vê-los.

A ideia em uma frase

Dentro do VPS, o Docker monta redes de computador de software: cada rede é um switch virtual, cada container é como um computador ligado a ela, com IP próprio. Uma conexão é sempre IP mais porta; com IPs diferentes, a mesma porta 8080 em dois containers são dois destinos diferentes, como dois apartamentos de número 8080 em prédios diferentes.

O mapa das redes

Clique num container para ver as redes dele, os IPs, a porta e com quem ele consegue conversar.

Peça da redeO que éNo VPS
Switch virtual (bridge)Cada rede do Docker é um switch de software. Quem está ligado a ele conversa; quem não está, não enxergaDuas: a da aplicação, criada pelo compose, e a coolify, onde ficam o banco e o Traefik
Placa de rede virtual (veth)Cada container ganha uma por rede, com um IP da faixa daquela redeA API, ligada às duas redes, tem duas placas e dois IPs
DNS interno (127.0.0.11)Traduz o nome do serviço no IP do container, como o DNS da internet faz com os domíniosPor isso o nginx escreve api:8080, e não um número: o IP muda a cada deploy, o nome não
Saída para a internet (NAT)O container sai "emprestando" o IP do VPS; a resposta volta pelo mesmo caminhoÉ assim que a ETL baixa os arquivos das fontes
Porta publicada (ports:)Liga uma porta da máquina a uma porta do containerSó o Traefik (80) e o painel do Coolify (8000, 6001, 6002). Nenhum container da aplicação

Quem decide as redes e quem entra em cada uma é o docker-compose.prod.yaml: os serviços com networks: [default, coolify] ficam nas duas, os sem networks só na da aplicação.

O caminho de um request

Escolha o que o visitante pede e avance passo a passo. Repare que, nos pedidos à API, as duas cópias se revezam (round robin): rode duas vezes seguidas.

O DNS interno

Dentro de um container da rede da aplicação, um nome vira um IP antes de qualquer conexão. Pergunte:

Publicar uma porta no VPS

Um container só ocupa uma porta da máquina se o compose mandar, com ports:. Experimente:

# sem ports: o container só existe na rede interna (todos os da aplicação)
api:
  build: …

# com ports: a porta 5000 do VPS passa a levar à 8080 deste container
servico-novo:
  ports:
    - "5000:8080"

Por que o firewall é o do painel da Hostinger, e não o do Ubuntu: ao publicar uma porta, o Docker cria regras próprias no sistema que passam por cima do ufw. Um ports: esquecido ficaria aberto para a internet com o ufw dizendo que não. O firewall do painel fica fora da máquina, e o Docker não o alcança.

Para ver os de verdade, no VPS

As portas de cada container. Seta (0.0.0.0:80->80/tcp) quer dizer publicada no VPS; sem seta (8080/tcp), só dentro da rede:

docker ps --format 'table {{.Names}}\t{{.Ports}}'

As redes, e os IPs de um container em cada uma:

docker network ls
docker inspect $(docker ps -q --filter "name=api-") --format '{{range $rede, $c := .NetworkSettings.Networks}}{{$rede}}: {{$c.IPAddress}}{{"\n"}}{{end}}'

O que o DNS interno responde, de dentro de um container:

docker exec $(docker ps -q --filter "name=etl-") getent hosts api api2

Quem ocupa cada porta da máquina:

sudo ss -tlnp
