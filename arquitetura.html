Chamar o VPS direto, sem passar pela Cloudflare

A Cloudflare esconde o endereço do VPS, mas esconder não é bloquear. Com o firewall aceitando a porta 443 de qualquer lugar, quem descobrir o endereço chama o VPS direto e pula a Cloudflare: sem filtro de ataque, sem cache e sem limite de taxa. O endereço vaza com facilidade: históricos de DNS, e-mail enviado pelo próprio servidor, varreduras que testam os endereços da Hostinger.

O banco continua inalcançável em qualquer caso. O risco é para o site e a API.

FormaComo funcionaPrós e contras
1. Túnel da Cloudflare
recomendada		 Um programa da Cloudflare dentro do VPS abre uma conexão de saída até ela, e as visitas chegam por esse túnel. As portas 80 e 443 ficam fechadas para a internet inteira. Não existe caminho direto para ninguém, mesmo sabendo o endereço. Gratuito, com suporte pronto no Coolify. Contra: a rota e o certificado passam a depender da Cloudflare.
2. Firewall só com os endereços da Cloudflare O firewall da Hostinger aceita a 443 apenas das faixas de IP que a Cloudflare publica. Simples e comum. Contra: a lista muda de vez em quando, e qualquer conta da Cloudflare sai pelos mesmos endereços.
3. Certificado de cliente da Cloudflare A Cloudflare apresenta um certificado próprio em cada conexão (Authenticated Origin Pulls), e o Traefik recusa quem não o tiver. Fecha a brecha da forma 2; as duas juntas são a alternativa ao túnel. Contra: mais uma configuração no Traefik.

Em qualquer forma: o Traefik só responde aos domínios do site. Quem chamar pelo número de IP não é encaminhado a lugar nenhum. O SSH (porta 22) fica aberto a qualquer endereço, porque o autor viaja e um IP fixo o trancaria fora; a proteção vem da chave, como abaixo.

Traefik e Coolify

Traefik é a porta de entrada dentro do VPS: todo acesso passa por ele, e ele decide para onde mandar. /api/* vai para a API, o resto para o site, o endereço do painel para o Coolify. Ele também guarda o certificado do HTTPS do lado do servidor e troca a versão no deploy sem derrubar o site.

Coolify é o painel que sobe e derruba os containers no VPS: liga o repositório, cria a API, o site e o banco, guarda os segredos e publica cada versão nova. O Traefik vem com ele: não se instala nem se configura à parte, as rotas se definem no painel. (O Coolify também aceita o Caddy no lugar do Traefik; o padrão, e o plano, é o Traefik.)

O passo a passo, do VPS vazio ao painel aberto, está no Roteiro do servidor, no fim desta página.

O painel do Coolify não fica exposto

O painel tem poder total sobre o servidor: sobe e apaga containers, lê todos os segredos e alcança o banco. Quem entrar nele leva tudo. Por isso ele não deve ter endereço na internet.

O deploy automático não depende do painel público: é o CI chamando a API do Coolify com um token, por um caminho próprio e mais restrito.

CI e CD

CI (integração contínua) é conferir: a cada git push, o GitHub Actions baixa o código e verifica se ele presta. Os roteiros já existem em .github/workflows/:

RoteiroO que confere
Back (.NET)Compila a API, roda os testes de unidade (entre eles o da polaridade dos votos), gera o script da migration e monta as imagens da API e da migration
ETL (Python)Roda os testes que não precisam de banco e monta a imagem da ETL
Front (React)Verifica os tipos, roda os testes e monta o site

Os testes de integração, que sobem um Postgres de verdade, rodam na máquina do autor, não no CI.

CD (entrega contínua) é publicar: o Coolify recebe a versão nova, sobe ao lado da antiga, confere que ela responde, faz o Traefik mandar as visitas para a nova e desliga a antiga. O site não sai do ar.

Do jeito padrão, os dois começam juntos no mesmo push, e o Coolify publica sem esperar os testes (P23). Neste projeto isso pesa: um erro na polaridade dos votos não aparece na tela, aparece como uma afinidade plausível e errada.

O fluxo recomendado, numa fila só:

  1. O push dispara o CI: testes e montagem das imagens.
  2. Só se tudo passou, o CI publica as imagens no registro do GitHub (ghcr.io), com a etiqueta do commit.
  3. No fim, o CI chama o Coolify para publicar aquela etiqueta. A publicação automática do Coolify fica desligada.
  4. No VPS, a migration do banco roda antes de a API nova subir. A API nunca migra o banco sozinha.

Roteiro do servidor

Do VPS vazio ao painel do Coolify aberto pelo túnel, na ordem, e como conferir cada passo. Linhas com PS> rodam no PowerShell do computador do autor; as outras, no VPS.

Reinstalar o sistema do VPS apaga tudo: usuário, chaves cadastradas, configuração do SSH, fail2ban e o que estiver instalado. E troca a impressão digital do servidor: o SSH do computador passa a recusar a conexão com o aviso REMOTE HOST IDENTIFICATION HAS CHANGED. Depois de reinstalar, o roteiro recomeça do passo 2.

1. Chave SSH, no computador do autor

PS> ssh-keygen -t ed25519 -C "igor-notebook-hostinger"

Saem dois arquivos em C:\Users\igorl\.ssh\. O .pub é a chave pública: uma linha que começa com ssh-ed25519 e pode ser mostrada a qualquer um. O sem extensão é a privada e nunca sai do computador. Uma chave por computador: se um notebook se perder, apaga-se só a linha dele no servidor.

Na conexão, o servidor manda um desafio e o computador o assina com a privada; o servidor confere com a pública. A chave privada não trafega pela rede.

2. Criar ou reinstalar o VPS

No hPanel, escolher o sistema e colar a linha inteira do .pub no campo de chave SSH. A Hostinger oferece modelos com o Coolify já instalado. Um modelo com outro aplicativo atrapalha: um Traefik avulso, por exemplo, disputa as portas 80 e 443 com o Traefik que o Coolify traz.

Se o servidor já existia, apagar a impressão digital antiga antes de conectar:

PS> ssh-keygen -R IP-do-VPS

E conferir a nova pelo terminal do navegador do hPanel, que não depende do SSH. Ela tem de ser igual à que o SSH mostra na primeira conexão:

ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub

3. Primeira entrada, como root

PS> ssh root@IP-do-VPS
apt update && apt upgrade -y

Se pedir senha, a chave não foi aceita. Não insistir em senhas: entrar pelo terminal do navegador e colar a linha do .pub em /root/.ssh/authorized_keys.

4. Usuário próprio com a mesma chave

adduser igor
usermod -aG sudo igor
mkdir -p /home/igor/.ssh
cp /root/.ssh/authorized_keys /home/igor/.ssh/
chown -R igor:igor /home/igor/.ssh
chmod 700 /home/igor/.ssh && chmod 600 /home/igor/.ssh/authorized_keys

A senha do adduser é a do sudo, não a do SSH. Conferir numa segunda janela, sem fechar a primeira: ssh igor@IP-do-VPS entra sem pedir senha, e sudo whoami responde root.

5. Desligar o login de root e o login por senha

sudo nano /etc/ssh/sshd_config.d/99-endurecer.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
sudo sshd -t && sudo systemctl restart ssh

O sshd -t recusa arquivo com erro antes de reiniciar. Conferir numa janela nova: ssh igor@… entra e ssh root@… é recusado.

6. fail2ban

sudo apt install -y fail2ban
sudo systemctl enable --now fail2ban

Bloqueia por um tempo o endereço que erra o login várias vezes. A configuração padrão já cobre o SSH.

7. Firewall no painel da Hostinger

No hPanel, em Segurança, Firewall: aceitar entrada só em TCP 22, 80 e 443. Usa-se o firewall do painel, não o ufw do sistema: o Docker cria regras próprias e passa por cima do ufw, então uma porta publicada por um container fica aberta mesmo com o ufw dizendo que não. O do painel fica fora da máquina. Conferir de fora:

PS> Test-NetConnection IP-do-VPS -Port 22      # TcpTestSucceeded : True
PS> Test-NetConnection IP-do-VPS -Port 8000    # TcpTestSucceeded : False

8. Coolify

Se o modelo do VPS já o trouxe, conferir que está de pé; se não, instalar:

sudo docker ps
curl -fsSL https://cdn.coollabs.io/coolify/install.sh | sudo bash

O docker ps tem de listar coolify, coolify-proxy (o Traefik dele), coolify-db, coolify-redis e coolify-realtime. Um Traefik que não seja o coolify-proxy sai antes da instalação: docker compose down na pasta dele, ou docker rm -f com o nome. O endereço http://IP:8000 que o instalador mostra não abre, e não deve abrir: a porta foi fechada no passo 7.

9. O painel, pelo túnel SSH

O túnel liga uma porta do computador do autor à mesma porta dentro do VPS, por dentro da conexão SSH. Para o servidor, o acesso vem dele mesmo, então o firewall não participa, e só abre o túnel quem tem a chave. Em C:\Users\igorl\.ssh\config:

Host coolify
    HostName IP-do-VPS
    User igor
    IdentityFile ~/.ssh/id_ed25519
    LocalForward 8000 localhost:8000
    LocalForward 6001 localhost:6001
    LocalForward 6002 localhost:6002
PS> ssh coolify

Com essa janela aberta, o painel fica em http://localhost:8000. A 6001 leva as atualizações ao vivo do painel (estado do deploy, logs) e a 6002 o terminal dele; só com a 8000, o painel abre mas não se atualiza sozinho. Criar a conta de administrador logo em seguida: até ela existir, quem abrir o painel primeiro a cria.

10. Proteger o painel

Em Settings: o domínio da instância fica vazio (o painel continua só pelo túnel) e "Registration allowed" desligado. No perfil, a verificação em duas etapas ligada. Em Sources, o GitHub App com acesso só ao repositório poligraph.

11. O banco

No projeto registro-aberto, ambiente production: + New, Database, PostgreSQL, com a mesma versão maior do banco local (a cópia da P87 não volta para versão mais antiga). Banco poligraph, usuário poligraph, senha gerada pelo Coolify, e "Make it publicly available" desligado. Da Postgres URL (internal) sai a connection string no formato do .NET:

postgres://poligraph:SENHA@NOME:5432/poligraph
Host=NOME;Port=5432;Database=poligraph;Username=poligraph;Password=SENHA

O NOME é o do container na rede coolify, não um IP. A senha não passa por chat nem por arquivo: vai do painel do banco direto para a variável.

Em production, Shared Variables: um lugar só para o que a API, a migration e o site usam. Na aplicação, cada variável aponta para a compartilhada com {{environment.NOME}}.

13. A aplicação

+ New, Docker Compose, repositório poligraph, branch master, arquivo /docker-compose.prod.yaml. Ele monta três serviços a partir dos Dockerfiles de docker/:

  1. migrations aplica as migrations e as perguntas da curadoria e termina. Roda a cada deploy; sem migration nova, só confere.
  2. api sobe só depois de a migration terminar bem, com o volume chaves-da-sessao: sem ele, cada deploy troca as chaves e desloga todo mundo.
  3. web é o site, o único com domínio. O nginx dele manda /api/ ao serviço api.

No Coolify, o domínio vai só no web, com a porta do nginx: https://registroaberto.org:8080 (a porta diz ao Traefik onde o container escuta; o visitante continua na 443). "Connect to Predefined Network" fica desligado: ligado, o Coolify renomeia os serviços e o site deixa de achar a api. A rede do banco já entra pelo próprio compose.

Antes do primeiro deploy, a cópia do banco local (P87), com o banco vazio: se a migration rodar antes, as tabelas já existem e o pg_restore entra em conflito.

PS> pg_dump -Fc --no-owner --no-acl -h localhost -p PORTA -U postgres -d poligraph -f poligraph.dump
PS> scp poligraph.dump igor@IP-do-VPS:/tmp/
docker cp /tmp/poligraph.dump CONTAINER_DO_BANCO:/tmp/
docker exec -it CONTAINER_DO_BANCO pg_restore --no-owner --no-acl -U poligraph -d poligraph /tmp/poligraph.dump

Depois, apagar o .dump nas duas pontas. A POLIGRAPH_CHAVE_CPF da ETL em produção tem de ser a mesma do local: os cpf_hash copiados foram calculados com ela.

Compose processa os três serviços a cada deploy, com alguns segundos sem API. É a escolha para subir rápido (decisão do autor, 2026-10-15); quando o CI publicar as imagens (P23), cada peça vira aplicação própria, sem queda.
